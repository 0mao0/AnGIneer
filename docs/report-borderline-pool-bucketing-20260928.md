### 3.0 新根因：判官评分「双刻度」，0.0x 家族=刻度误读（09-28 探针顺带挖出，优先于双判）

探针原始日志（/tmp/judge_probe.log）里判官输出的 score 分布：`"10"`×16、`"0.8"`×6、`"8"`×3、`"9"`×2、`"7"`×1、`"0.7"`×1。**同一批调用里判官在两种刻度间抽签**：0–10 整数（多数）与 0–1 小数（7/29 次）。

消费端：deepeval 4.2.3 在未传 rubric 时假定 0–10（`get_score_range(None)=(0,10)`，g_eval.py:402），并做 `score=(g_score-0)/10`（g_eval.py:153/215）。于是判官答 `"0.8"`（本意「良好」）被算成 **0.08** → 判 wrong。探针 30 次调用里 6 个 0.08 与 1 个 0.07 与原始日志的 `"0.8"`×6+`"0.7"`×1 **逐一对上**，且这些行的判词均为正面（"fully captures…"）——刻度误读坐实。

池内规模：99 池 522 行明细里 sem∈(0,0.1] 共 **47 行（9.0%）、涉 40 题**；其中至少一晚「×10 后 ≥0.8」的题 **14/135（池+凌晨并集口径）**。即 D 桶「0.06–0.08 灾难分」一整族主要是这个刻度 bug，而非判官对内容的真实否定。

**P0 实施记录（09-28）**：`judge_deepeval._normalize_judge_score_scale`（仅 `0<score<1` 时 ×10 并写回整数；`score==1` 语义两可不动），接入 `DGXJudge.generate` 的 schema 分支；原始分与命中标记留痕（`judge_raw_score` / `judge_scale_fixed` 进 details）；`caliber_fingerprint` 增 `judge_scale_fix` 版本位（v1）防续跑缝合；单测 `tests/test_judge_scale_fix.py` 5 例 + 判分链定向 56 例全绿。legacy 判分路径无此 bug（其 clamp 语义天然把 0.8 读成 0.8），未动。已提交 `d839236` 并 docker cp 入生产容器（**未推送、未重启**：长驻进程仍旧码，夜间生效需 restart；仓库未推送前，下次部署重建容器会退回旧码）。

> **09-29 勘误（本段两处已过期，勿再按此转述）**：`d839236` 随后进 origin/main——`git tag --contains d839236` = v0.2.82 与 v0.2.83 两个 tag 都含它；容器于 09-28 22:56（BJ）由该次部署重建，生产镜像内 `_normalize_judge_score_scale` 在场（09-29 实查）。即「未推送」与「重建容器退回旧码」两条风险均已解除，生产判分是代码版而非 docker cp 副本。

**对方案的影响**：修复刻度（P0，零运行成本）应排在双判投票（P1）之前；P0 后重跑探针再定量残余。**根因链更新为**：生成换文（100%）→ 判官刻度误读（0.0x 家族，可零成本修）+ 判官贴闸摆动（0.7↔1.0，需投票/双判）+ 判官看漏/误伤（N 桶工程修）。
