## 0. 一句话

M0 不是「要不要做 B」的守门（B 已立项），而是**用最低成本把「图到底补了什么」量出来**。
为此需要三条臂，而不是两条：现状 A-min、指针骨架、会话图。

## 1. 三臂定义（跑前锁定，跑中不得改）

| 臂 | 定义 | 工程量 | 改哪里 |
| --- | --- | --- | --- |
| **臂 1 = A-min（现状）** | 线上现状：历史 tool 消息超预算时压成 `[已压缩: 工具 xx 的结果，要点: 检索到 N 条候选]`；user/assistant 全带 | 0 | 无 |
| **臂 2 = 指针骨架** | 同臂 1，但压缩行的「要点」换成**确定性指针**。⚠️ **两处必须钉死（2026-10-04 评审修正）**：① **标记前缀是三类不是一类**——`knowledge_search` 用 `K`、`table_search` 用 `T`、`entity_search` 用 `E`（`agent_tools.py:_assemble_search_result` 的 `prefix=`），正则一律 `\[([KTE])(\d+)\]`；只抽 `[Kx]` 会漏掉 **23.0% 的被引用 item**（实测 3,289 条带 cite：K 2,533 / T 756）→ 臂 2 被系统性低估。② **实现变体二选一，跑前定**（见下方「臂 2 变体」） | (i) 半天～1 天 / (ii) ≈1 小时 | （见变体表） |
| **臂 3 = 会话图** | 同臂 1，历史 tool 原文不进 prompt，改由会话图子图渲染段 + 指针回引承接（BB §2.3/§3/§4）。⚠️ **M0 的臂 3 必须自带通道 1**（2026-10-04 评审修正）：**离线直连 docs-core store 层 `canonical_sql_store.list_blocks_by_clause_refs`**（`clause_id` 有索引，现成），**不等** `fetch_clause` 的 HTTP 端点（那排在 M1）。否则臂 3 缺指针召回 → vs 臂 2 的差值被低估 → 「收缩边界」可能是**假阴性** | 其本体工作量（BB §9），M0 阶段只做离线可调用版 | 新增图模块（离线复用路径） |

**臂 2 变体（跑前锁定，选定后不得换）**

| 变体 | 做法 | 量级 | 语义 |
| --- | --- | --- | --- |
| **(ii) 候选指针行（默认采用）** | 压缩时直接输出该 tool 消息**前 k 条 items** 的 `doc_title + (clause_id\|section_path)`，纯函数、只吃 `message.meta` | ≈1 小时 | 贴的是「**检索到的**」——覆盖 K/T 两类，零 run 划界风险 |
| (i) 精确引用 join | 扫 run 边界 → 找该 run 的 assistant 原文 → 抽 `[KTE]x` → 与 items 的 cite 对齐 | 半天～1 天 | 贴的是「**被引用的**」——最贴 BB §3.2 原文语义，但 `transform_context` 签名只有 messages（`agent_loop.py`），run 划界要自己扫且要绕开注入 user 提示 |

选 (ii) 的理由：M0 要回答的是「证据结构值多少分」，(ii) 已能回答；且 (i) 多出来的只是「精确到被引用」这一层，留作 M2 的候选升级。

**臂 3 的指针回引机制（跑前锁定，二选一）**

| 机制 | 说明 | 代价 |
| --- | --- | --- |
| **召回层预取注入（M0 默认）** | 序数/指示代词消解命中节点后，离线壳**直接取回原文块**拼进子图渲染段 | 确定性、不吃轮次预算 |
| 模型可见工具自捞 | 给模型一个 `fetch_clause` 工具，由它自己决定调 | 吃 `max_turns=3` 的轮次预算；两种测出的增益不是一回事 |

**禁例（沿用 BB §11）**：不得把臂 2 当「值不值得做」的秤，也不得当臂 3 的退路。
它的身份是**构件**——图写入路径本来就要写同一段 join，图的 clause 节点 key 只能从它来。

**⚠️ 落地纪律（2026-10-03 补）**：臂 2 进代码时**必须带开关**（建议 `ANGINEER_POINTER_SKELETON`，默认关）。
理由：一旦无条件生效，生产里就再也找不到「臂 1 = 现状」，M0 无法逐题对照，也失去一行回退——
而臂 1 正是本预注册里的基线与唯一参照。开关同时服务于 M0 的臂选择与上线回滚。

**⚠️ 落地纪律 ②（2026-10-04 评审补）：蒸馏入口必须是一个可调用的函数，不许内联在 SSE 分支里。**
理由：M1 的挂载点只有 `main.py` 的 `run_end` 分支，而 §7.6 的多轮评测若沿用
`_query_helper.run_eval_query`（直连 `run_policy_query`、不走 SSE），**蒸馏根本不触发**——
评测测到的会是「图是空的」的残血臂 3。所以入口定形为
`conv_graph.distill_run(owner_key, session_id, run_id, slice_messages, library_ids) → ops`：
SSE 的 run_end 调它，离线壳（M0）与评测基建（M3）也调它。

**⚠️ 落地纪律 ③（2026-10-04 评审补）：蒸馏读内存切片，水位在 persist 之后。**
`hist_list[hist_base:]` 的内存切片就是本轮真相（与 BB §3.1 一致），**不要重读 chat.sqlite**——
客户端断连兜底支的 persist 是滞后的，重读会拿到不含本轮的库。水位（`conv_graph_state`）
推进放在 persist 成功之后；即便顺序出错，也由 `run_id` 幂等兜底，不得让水位先于落库前进。

## 4. 判分口径（跑前锁定）

- **判分人**：业主本人（他就是领域专家，也是当前唯一用户）。
- **呈现方式**：三臂答案**盲序**呈现——每题三份答案随机打乱（去掉臂名与时间戳特征），
  逐题独立判分，**禁止跨题对比**；判分人不知道哪份来自哪一臂。
- **粒度**：每题每臂记 ✅对 / ⚠️部分对 / ❌错 / ⛔未答（拒答或无证据），并写一句理由。
- **留痕**：答案完整文本 + 理由 + 该臂该题的运行时间与该轮 `cached_tokens`。
- **禁止**：判分过程中改题目、改口径、改模型配置；发现题目有歧义 → 标记作废并补题，
  作废题不计入分母（补题也要重新过一遍三臂）。

## 5. 判定规则（预注册阈值，跑前锁死）

| 判据 | 阈值 | 结论 |
| --- | --- | --- |
| 臂 1 vs 臂 2 | 臂 2 净改善 ≥3 题且净回归 = 0 | 「指针骨架」本身就有明显价值 → 它的落地不受 M0 其余结论影响（本就该做） |
| 臂 3 vs 臂 2（**核心**） | 差值为 0 或为负 | 图的边界**收缩**到指针覆盖不到的部分：derives 链、值复用、未决跟踪、导航（M4） |
| 同上 | 臂 3 净改善 ≥3 且净回归 = 0 | 按 BB §8 M1-M3 全量推进 |
| 臂 3 / 臂 2 vs 臂 1 | 净回归 >0 | 先修证据层（召回或蒸馏），**设计调整后重跑 M0**，不停工 |
| **臂 3 vs 臂 2（中间档，2026-10-04 评审补）** | **净改善 1~2 题且净回归 = 0** | **不得直接下结论**——按下面「中间档裁决」处理；n=22 下落进这一档的概率不低，原稿此档是真空 |
| 蒸馏链路 | 失败率 >20% 或单轮 P95 > 30s | 链路不可用 → 先解决模型/配额（BB §3.5）再谈图 |

「明显改善」的统一定义（三处引用同一句）：**净改善题数 ≥3 且净回归 = 0**。

**中间档裁决（跑前锁死，跑中不得改口径）**：臂 3 相对臂 2 净改善 1~2 题时，按**题型分层**读：

1. 若改善集中在 **A 类（序数/指示代词指涉）**——图 + 指针的靶心题型——则**推进 M2**，
   并把 A 类作为 M2 的主验收面；其余类型记为「未观测到增益」，写进结论但不否决。
2. 若改善集中在 **C 类（条款回引）**且明显占优（该类型内 3 题以上优于臂 2），同样推进，
   理由是这类恰是「证据结构化」的直接靶面。
3. 若改善**分散且无法归因到任何题型**，或同时伴随任一题回归 → **补题重跑**（n 从 22 加到 ≥32，
   新增题仍按 §3.5 规则确认后冻结），不得用「差不多」收口。

> 中间档不设「再做一次看看」这类自由裁量——上面三条是穷举，落哪条由**题型分布**决定，
> 不由跑数人的印象决定（这是预注册的意义）。
