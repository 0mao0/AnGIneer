## 2. 证据（可在部署机 nginx 复核）

服务器 `124.221.238.70:/var/log/nginx/ai-upstream.log`（及轮转 gz），字段含
`status / upstream / upstream_time / ua="OpenAI/Python 1.109.1"`（ua 为该 ua 仅 AnGIneer 管线流量）：

- 09-28 今日 popo 状态码分布：`439×200，36×400，1×404`（404 为调用侧探针误用模型名，忽略）；
- 典型 400 行：`status=400 upstream_time=6.5~62s`——**DGX 处理数秒到 1 分钟后拒绝，不是连接层的瞬时挂**，
  与「服务抖动」形态不同；
- 09-27 晚（gz 内）：`1036×200，41×499，26×502，10×400`。

### 2.1 400 的根因已复现（重点，非猜测）

调用侧用超长 prompt 直接复现，拿到 DGX 返回体：

```
POST /api/popo/v1/chat/completions  (prompt ≈ 2.5 万 token)
→ 400 {"error":{"message":"This model's maximum context length is 16384 tokens.
   However, you requested 16 output tokens and your prompt contains at least 16369 input tokens ...
   (parameter=input_tokens, value=16369)","type":"BadRequestError","code":400}}
```

即：**今日 36 个 400 ≈ 长页文档的请求超过了 `max_model_len=16384` 被确定性拒绝**。
这不是随机「抖动」——同一篇文档重跑多少次都会 400（调用侧 09-28 上午对同一文档 3 次退避重试全灭，与此吻合）。

上下文：MinerU-Popo 的页级后处理输入是整页 markdown，英文财报长表格页轻松超 16k token；
调用侧客户端目前按 10 万字符截断（上游惯例），与 16384 token 的服务侧上限存在**契约不匹配**。
