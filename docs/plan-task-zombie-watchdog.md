# 任务假死看门狗 · 施工单

> 2026-10-14 起草。状态：**待拍板**（未动工）。适用于 docs-core 解析编排器（本地 docs-api 与生产同码，两边受益）。

## 0. 一句话

给解析流水线加「任务没推进就自动判死」的看门狗：把现在的**人工发现 → 重启 docs-api 清线程 → 重建队列**（小时级、在跑全废），换成**自动判死 → 单任务失败可重试 → 队列不受影响**（分钟级）。

## 1. 背景：三个卡死现场与「逃生口全断」

| 现场 | 症状 | 根因层 |
|---|---|---|
| LLM 标题仲裁（2026-10-14 上午） | 5 个任务挂死在 `_llm_arbitrate_title_levels → llm_client.chat`，最长 3.3 小时；16 篇白等 5 小时 | 本地任务环（无推进检测） |
| MinerU 请求（2026-10-14 凌晨） | 引擎端被内核 OOM 杀掉，客户端 HTTP 静默挂死 36 分钟 | 远端（已被 inference-guardian 治）+ 客户端无检测 |
| popo 引擎冻结（10-12，24.5 小时） | 远端 `/health` 仍 200，请求永不返回 | 远端（已有守护）+ 客户端无检测 |

**为什么现有机制全断**（已核代码）：

- `cancel_parse_task`：置取消标志 + `_cancelled.add` + `parser.cancel()`（abort 事件）——但 worker 卡在阻塞调用里**永远走不到取消检查点**，取消无效（今天两次实测）。
- `retry_parse_task`：节点 processing 时若 `thread.is_alive()` → 直接拒绝「正在解析中，请先取消当前任务」——**卡死线程恰好 alive**，与取消无效叠成死锁：既不能取消、也不能重试。
- 唯一逃生口 = 重启 docs-api（杀线程），在跑任务全废。

结论：**「线程活着但零推进」没有任何机制发现它**——看门狗填的就是这个洞。

**等待的三类拆解（10-14 晚补，数据复核后）**：把「16 篇白等 5 小时」拆开看——

1. **正常容量排队**：6–8 篇 70 分钟级 MinerU 在 2 槽位上串行 ≈ 4.5 小时（真工作量，任何调度都绕不过）；
2. **旧闸门钉住（排队等待放大器）**：popo 闸门 12:10 → 13:47 出现 **97 分钟零开工**（当时 popo 全空、cap=4），
   13:47 重启后 ~13 篇在 40 分钟内鱼贯解锁——「一解锁全队动」是前沿钉住的签名（容量排队会均匀出队）。
   **该类已由方案 A（b261ac17）消除**；
3. **线程假死（本看门狗目标）**：卡在阻塞调用里零推进、取消/重试都摸不到它。

看门狗判据用「阶段工作墙钟」（不含排队等待），天然不会把 ①② 误判成假死。

## 2. 目标与非目标

- **目标**：自动判定假死 → 留证（线程栈）→ 标失败（可见、可解释）→ 放行重试 → 队列其余任务不受影响。
- **非目标**：强杀线程（Python 做不到）；远端引擎的看护（已有 inference-guardian）；检索/问答链路。

## 3. 判据与起始阈值

**主判据**（简单可靠）：阶段行 `status='running'` 且「工作墙钟」（`doc_parse_stages.started_at` → now，天然不含排队等待）超过该阶段上限，且对应任务线程仍存活。

**起始阈值**（取自本机全库历史完成行的 p99 与 max，留 3–4 倍余量；交付时逐个用生产数据复核）：

| 阶段 | 历史 p99 | 历史 max | 起始阈值 | 备注 |
|---|---|---|---|---|
| raw_parse | 42.9 分 | 124.3 分 | 180 分 | 大文档合法慢，阈值最宽 |
| popo | 17.1 分 | 26.5 分 | 60 分 | |
| structure | 16.6 分 | **156.5 分** | 45 分 | max 即 10-14 仲裁卡死现场 |
| vectors | 16.7 分 | 48.7 分 | 90 分 | 含 embedding 批量 |
| figure_describe | 12.5 分 | 14.0 分 | 30 分 | |

**辅助判据**（第二阶段再上）：细粒度心跳（每步 `ctx.log_step` 时间戳）；现有打点粒度粗（MinerU 全程仅 3–4 个步骤行），暂不足以做「无进度」判据。

## 4. 设计

组件：`docs_core/task_watchdog.py`（新模块）+ 编排器接线（注册/注销任务、提供线程与解析器句柄）。

```
ParseOrchestrator
  ├─ 注册表：_threads / _parsers / _cancelled（已存在）
  ├─ 看门狗线程（daemon，poll 60s）
  │    每轮：遍历在建任务
  │      ├─ 线程已死 → 跳过（retry 路径已有「旧任务中断」处理）
  │      ├─ 当前阶段 status=running 且 工作墙钟 > 阈值？
  │      │    否 → 继续
  │      │    是 → 连续 N 轮（grace，默认 2）→ 判定假死
  │      └─ 处置（观察模式下只做第 1 步）
  │           ① 打现场：sys._current_frames() 取该线程栈 → ERROR 日志
  │           ② 标失败：parse_tasks/节点 → failed，message="看门狗判定假死：X 阶段停 N 分钟"
  │           ③ 放行重试：_threads.pop(task_id)（retry 的 is_alive 检查即通过）
  │           ④ 防脏写：_cancelled.add(task_id) + parser.cancel()（僵尸醒来时经现有检查点中止）
  │           ⑤ 队列让位：闸门排队位 skip（运行中占用的槽不可强放——见风险）
  └─ 记录：判定与处置写日志 + parse_stage_steps 一行「看门狗判死」（前端步骤条可见）
```

**分两段上线**：先 `WATCHDOG_MODE=observe`（只打栈+告警，不改状态）跑一周校准阈值 → 切 `enforce`（完整处置）。

| T2 | 看门狗模块（观察模式）：扫描/判据/打栈/告警；编排器接线 | `task_watchdog.py` + 单测 | 假睡眠阶段超阈 → 告警一次、栈指向 sleep 点、**状态不变** |

## 6. 风险与前提

- **线程不可强杀**：处置后僵尸线程会遗留到其调用超时返回；因此 **T4（有限超时）是同批前提**——没有它，「僵尸存活多久」不可控（槽位会一直被占）。两者必须一起做。
- **槽位泄漏**：运行中占用的闸门槽不能强放（僵尸醒来会重复 release，把并发放大）。可接受代价：单次泄漏占 1 槽（mineru=2 / popo=4 / figure=2）；若频繁泄漏，运维仍可重启，但已是最后手段而非唯一手段。
- **误判**：阈值必须显著高于合法 p99.9（大文档 70+ 分钟合法）；观察期一周 + grace 两轮缓冲；误判的代价 = 单任务失败（可重试），不是数据损坏。
- **与闸门方案 A 的关系**：闸门修「谁先走」，看门狗修「卡住的那个怎么办」——互补，不重叠。
