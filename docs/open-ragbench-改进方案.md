# Open RAGBenchmark 评测改进方案

## 背景与结论

当前 OpenRAGBenchmark 子集（120 题）基线为 **86.7%（104/120）**，16 道错题全部落在图表/表格类，纯文本题已到 100%。这说明瓶颈已从模型回答能力转移到解析与索引管线。

16 道错题可归为三类根因，对应三条修法：

1. 表格内容没进检索索引（纯数值表无行级文本）
2. 表格有行文本但表头错位，数值标签是乱的
3. 图的内容根本没进管道（只留下 caption 引用句，图片本体丢失）

## 问题清单

### A 类：表格没进索引

库中 184 张表里，有 30 张 `numeric_dense` 表（行数 ≥ 5）只有一句“表格《未命名表格》包含 N 行、N 列”的摘要，没有行级文本。代表题目：OJV/BLS 州级就业差异（2412.19754v3，50 行州名与百分比全不可检索）。

### B 类：表头错位

有行文本，但多行表头（如 `#1/#2`）未合并、空表头列未处理，导致数值与列名错位。代表题目：MPC-ICCBF 碰撞率（Low 10.2%/1.9%，High 100%，但模型看到的是错位标签，只能定性回答）。

### C 类：图丢失

图片文件已解析到磁盘（例：蛋白模型文档 61 张图），但 `doc_blocks` 里 figure/unknown 块的 `image_path` 为空，正文只剩“Figure 10 展示了训练/评估损失曲线”这类引用句。代表题目：loss curves、SO2/PM2.5 热力图、beam patterns。

## 表格索引方案

核心原则：**向量索引存“可检索文本”，数字作为载荷跟随命中结果进入上下文，不单独做 embedding**。

| 表形态 | 进索引的文本 | 数字处理 |
| --- | --- | --- |
| 键值/枚举表 | 表头 + 行键 + 摘要 | 数值作为该行载荷 |
| 纯数值矩阵 | 摘要 + 行列头 | 完整矩阵进表级载荷 |
| 文本稠密表 | 文本行 | 照常 |

顺带修两个质量问题：合并多行表头（`#1/#2` 拼回父列名）；行 chunk 不再整段重复 caption，改用短标题或表摘要。

改动落点集中在表格语义生成（`table_semantics.py`）与 chunk 重建（`canonical_builder.py`），改后对受影响文档重建 chunk 与向量。

## 图像方案

前置步骤：把 MinerU/Popo 产出的 `images/` 重新关联回对应 block（`image_path`），先恢复“哪张图对应哪个 figure”。

主力路线：解析期 VLM 图描述入库。解析时对每张图生成文字描述（趋势、数值、结论），作为 figure 块的可检索文本进索引；查询时仍走纯文本，零额外延迟。项目内已有 Popo 的 VLM 图题步骤（`run_inference.py` / `image_caption` / `vlm` 目录），以接通和回填为主，不从零建设。

二期可选：查询期多模态问答，把原图交给多模态模型回答，保真度最高但延迟与成本更高。

## 落地顺序与验收

1. 先修表格索引（表头 + 行键 + 摘要进索引、数字进载荷、合并多行表头），重建受影响文档索引。
2. 修 figure↔image 链接，恢复图片路径。
3. 启用/修复 PoPo VLM 图描述，跑图题。
4. 顺手修判分 JSON 转义 bug（当前有 9 题语义判分解析失败被按满分计，影响分数可信度）。

验收题：OJV/BLS、MPC-ICCBF、hyperparams、loss curves 单题重测，目标是把整体正确率从 86.7% 往上抬；每完成一步重跑 120 题全量做前后对照。

## 范围与风险

只动解析/索引侧，不碰线上问答主流程与 agent 循环。重建索引需明确影响范围（本次仅 OpenRAGBenchmark 知识库），并保留原索引可回滚。
