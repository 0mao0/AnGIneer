# Harvey LAB 枚举型检索改造：文档级筛选 + 批量读页

状态：**已施工**（doc_search / doc_read / doc_catalog 上线），100 题复测进行中。
日期：2026-10-18。范围：`services/docs-core`、`services/docs-api`、`services/angineer-core`、`scripts/`。

## 1. 根因（实测，不是推断）

题目形态是枚举：「pull every one of our antitrust matters where we drew an HSR second request」。
语料 lab-firm-full = 266 个 matter / 9007 篇文档 / 约 250 万段落 chunk。

| 证据 | 数值 | 说明 |
|---|---|---|
| 精确 matter 名查询 | 9/9 命中 | 能查到「某篇已知文档」 |
| 主题查询（top-20 段落） | 0/9 覆盖全部 matter | 查不到「全部候选」 |
| 注入的首轮 knowledge_search | 15 条命中、**12 篇不同文档** | 段落级检索的文档覆盖面 |
| 题 001 需要的候选 matter | 6 个（真值） | 30 题样本 all-pass 6.7% |

结论：缺的不是相似度，是**文档级候选清单**。段落 top-k 的排序目标（最相关段落）
与枚举目标（覆盖全部候选文档）天然冲突；k 调大也解决不了分组与去重。

## 2. 方案

两层工具 + 一层元数据，全部复用既有 canonical 索引，**不重跑解析**。

### 2.1 数据层：`doc_catalog`（可选表）

`doc_catalog(doc_id, library_id, matter_id, folder, rel_path, filename, doc_type, source)`，
落在库组 index sqlite（`resolve_index_db_path`），`CREATE TABLE IF NOT EXISTS` 懒建，不迁移既有表。

- 有表：检索结果按 matter 归并，等于恢复官方 harness 里 `dms/matters/<matter>/<folder>/<file>`
  的目录信息面（我们的入库把目录扁平化成了文件名）。
- 无表：退化为按文档分组，功能不变。

回填脚本 `scripts/backfill_doc_catalog.py`：从导入清单的 `(rel, tier, doc_id)` 写元数据，
lab-firm-full 实测 9008 行 / 266 matter，耗时 < 1s，不触碰解析产物。

### 2.2 `doc_search`：文档级筛选

- FTS 命中按 **文档** 聚合（`canonical_chunk_fts` 明细取出后在 Python 侧聚合，
  因为 FTS5 的 `bm25()` 不能进 GROUP BY——实踩）；
- 查询计划三级：整串短语（权重 3）→ 相邻二元短语（权重 2，如 `"second request"`）→ 全词 AND（权重 1，仅在短语通道 < 5 篇时放开）；
- 文件名/路径通道：命中 ≥2 个 query 词或整串短语才计分（`hsr-filing-*` 这类泛词不算二次问询信号）；
- 输出按 matter 分组的卡片：`matter_id / n_docs / best.{doc_id,title,snippet} / docs[≤per_matter]`，
  默认 40 篇、最多 120 篇、最多 40 张 matter 卡；
- 实测（题 001，query `HSR second request`）：**147 篇候选 / 25 个 matter，真值 6/6 全在卡内**，
  单次结果约 10 KB（旧的 docs+matters 双份清单会到 25 KB，已删掉重复字段）。

### 2.3 `doc_read`：批量读页

- 一次最多 8 篇，`mode=head` 读开头、`mode=match` 读命中段落，每篇默认 1200 字符（上限 4000）；
- 输出带页码 `[pN]`，模型据此判断「真的收到二次问询」还是「仅为风险/预案」。

### 2.4 接入

- L1（`build_qa_config`）与 L3/L4（`build_complex_config`）工具箱都加入两件工具；
- HTTP 端点：`POST /api/knowledge/internal/doc-search`、`/internal/doc-read`，
  `DocsRetrievalClient` 新增同名方法，进程内回退走 `docs_core.step09_query.doc_search`；
- 预算闸默认从 160k 降到 120k：网关侧 qwen3.6-35b 安全容量只有 138,146 tokens，
  实测 155,582 tokens 直接 400 中断整题——停止线必须低于真实窗口。

|---|---|---|

## 4. 失败实验（已回退，留档）

把枚举纪律写成 **系统提示规则 16**（v19）后，qwen3.6-35b 在工具结果之后稳定退化为
「逐字回显用户问题」（4 次复现，答案长度恒等于题面 523 字符，`has_tool_calls=false`）。
同配置撤掉规则、只留工具描述即恢复正常。

结论：**枚举纪律放工具描述，不进系统提示规则清单**。`prompts/agent_configs.py` 里
v19/v6 只保留注释，不注册；`ANGINEER_QA_PROMPT_VERSION` 仍取 latest=v18。

## 5. 已知风险 / 下一步

1. **工具使用不稳定**：同一配置下模型有时只调 knowledge_search 就作答（题 001 复现）。
   下一步：把 doc_search 做成枚举题的**自动注入**（与赌博式预检同层），不依赖模型自觉调用。
2. **matter 元数据只在有 catalog 的库可用**：产品侧应在入库时保留上传路径/目录，
   当前只对 lab-firm-full 用清单回填。
3. **评测口径**：`doc_search` 的候选集依赖 query 词面；换写法（复数、缩写）召回会掉，
   二元短语 + 回退 AND 是兜底，不是语义等价。

## 10. P2.1 实验记录（2026-10-19，失败，默认关）

实现：evidence_binding——答案后置审计，一次 LLM 抽取「断言 + 逐字引文」，规则核验引文是否出现在本轮工具返回里，把无依据断言所在句子删掉。开关 ANGINEER_EVIDENCE_BIND 默认 0。

七题（001/005/009/031/041/045/080）：
- 基线 14/83=16.9% → P2.1 10/83=12.0%，all-pass 仍 0；
- 031 4/6→1/6（答案 11776→3887 字符）、045 4/13→2/13、005 3/6→2/6；041 +2；
- 001 仍未修好（输出 326 字符的题面片段）；001 单题耗时 533 秒（多一次大 prompt 的 LLM 调用）。

失败原因：
1. **按 matter 编号删句太粗**——同一编号在「支持」与「不支持」的句子里都出现，删一句连带删掉整段正确内容；
2. **抽取调用太慢**——答案 10k + 证据 24k 的 prompt，单题 +8 分钟，不可接受；
3. 只删不补——被删掉的断言没有替代写法，答案变短但没变对。

结论：P2.1 形态（后置 LLM 抽取 + 整句删除）不可用，默认关、代码保留。P2.2 改为生成期契约：答案每条断言自带 doc_id + 页码 引用，引用逐条解析校验，无引用的断言只标记不删除，必要时让模型补引文而不是盲删。


## 11. P2.2 实验记录（2026-10-19，契约未被执行，默认关）

实现：生成期引用契约——system prompt 末尾追加「每条断言以 [doc_id pN] 结尾，无依据写 [no-source]」；guard 只解析引用并对照工具结果核验，不改写、不删句。

三题（001/031/041）：
- 031：10409 字符，**0 条引用**；041：4987 字符，**0 条引用**；001 仍回显（523 字符）；
- 契约完全未被遵守，与 v19 规则 16 的表现同类（模型忽略系统提示尾部规则）。

结论：提示词层面的引用契约对 qwen3.6-35b 无效。证据绑定只有两条可行路径：
1. **结构化生成**：答案先产出表格（断言 | doc_id | 页码 | 引文），再由渲染器拼成散文——格式由代码约束，不依赖模型自觉；
2. **换模型**：用更强的模型做最终作答（A/B 验证）。

在此之前，P1/P3/P0.5/P2.1/P2.2 五次实验都指向同一结论：**问题不在检索，也不在提示词，而在「生成后没有可执行的校验与修复结构」。**

## 13. 时间维度：doc_catalog 日期列 + doc_search 日期排序（2026-10-20，机制落地、效果未证）

动机：Qwen3.8 臂剩下的 0 判据题里 13/16 问「最近/最新/多少」，缺的是「按时间找最新一篇」而不是语义相似。计划与设计见 [plan-harvey-time-dimension.md](plan-harvey-time-dimension.md)。

做法：
- `doc_catalog` 加 `doc_date/date_source/date_confidence`（懒 ALTER；`scripts/backfill_doc_dates.py` 回填，不重跑解析）；
- 抽取优先级 正文首屏日期（high）→ 文件名日期（medium）→ 仅年份/年月（low）→ mtime（low）；未来日期与英文孤立年份丢弃（引证页码/表格单元格噪声）；
- `doc_search` 加 `sort_by=date_desc|date_asc`、`date_after`、`date_before`，默认不传参逐字节不变；mtime 不参与排序主序与区间过滤。

数据（lab-firm-full，9009 篇）：text 3726 / filename 159 / mtime 5124；high 3726 / medium 57 / low 5226；1998-06-12 – 2026-10-15。

评测（Qwen3.6-35B、gpt-5.5 判官）：

| 臂 | 16 题 criterion | 离开 0 判据 | 001–030 criterion |
|---|---|---|---|
| `time16-before`（同 HEAD，工具 schema 不带日期参） | 8/46 = 17.4% | 2 题（004/069） | — |
| `time38`（带日期参） | 10/46 = 21.7% | **4 题**（004/018/044/069） | 25/206 = 12.1%（10-18 臂 21/206） |

读法：+2 条判据 ≈ 0.7 个标准误，不显著；16 题里只有 4 题真的用了 `sort_by=date_desc`（25%，低于 50% 阈值），而加分的 4 题都没调 `doc_search`——**本轮不能归因于时间维度**。

两个结构性缺口（下一步）：
1. 工具选择：目标题多数直接走 `knowledge_search`，进不了 `doc_search`；需要对「最新/最近」做路由级预取（P0.5 形态，默认关）；
2. 候选集太宽：全局日期排序会把实体型问题的目标 matter 挤后（013：相关性第 13 → 日期第 37，判据 1→0）；需要 matter/客户过滤参数，让「实体内最新」一次调用完成。

原计划验收「≥5 题离开 0 判据」本轮为 4 题，**未达标**；001–030 无回归（+4 条，对照 10-18 臂）。

### 13.1 预取注入复测（2026-10-20 晚，负结果）

按风险表补了 `date_prefetch`（日期意图 → 复用枚举改写 → `doc_search(sort_by=date_desc)` → 注入 ≤15 组候选），默认关。16 题配对：

| 臂 | criterion | 日期参数使用 |
|---|---|---|
| 对照（schema 不带日期参） | 6/43 = 14.0% | 0/16 |
| 只开日期工具 | 10/43 = 23.3% | 4/16 |
| 预取注入 | **4/43 = 9.3%** | 11/16 |

注入把参数使用率拉到 11/16，却让判据数下降——模型把预取候选当成候选全集，自己不再检索（018/040/044/069 回落）。结论：**预取注入保持默认关**；工具选择瓶颈改由「实体/案件过滤参数」解，不再往系统提示词塞候选。

### 13.2 `entity_contains` 实体内取最新（2026-10-20 深夜）

`doc_search` 增 `entity_contains`：FTS 定位提到实体的文档 → 经目录映射到 group → 候选只在实体 group 内，再按 `filename_contains`/日期排序；组内 `best` 在给了 `filename_contains` 时取命中文档。

手工验证（lab-firm-full）：`entity_contains="Lumos Analytics", filename_contains=["credit agreement"], sort_by="date_desc"` → 唯一候选 `1008-00001 / credit-agreement-execution.docx (2023-03-09)`，正是题 013 的答案文档。015 等「客户 + 某类文件 + 最新」可用同一组合表达。

冒烟：模型第二次调用用上了这三个参数并拿到正确卡片，但最终答案改答 SAFE（未采用检索到的信贷协议）；gpt-5.5 判官端点两次挂起，未出分。结论：检索侧已解决，剩余是「拿到正确卡片后如何作答」——下一步做 L1 强制先走该组合并把结果作为首选证据（需新对照臂）。

### 13.3 `authoritative` 卡片与 `doc_read` 读页修复（2026-10-20 深夜）

- `authoritative`：entity+filename+`sort_by` 唯一命中时，`doc_search` 返回 `authoritative={doc_id,title,doc_date,instruction}`，明确「必须基于该文档作答」。冒烟中模型确实改了行为：用上组合参数、拿到唯一卡片、并 `doc_read` 了该信贷协议。
- `doc_read` 两个坑：全词 AND 匹配（"MFN Most Favored Nation"）0 命中 → 回落整篇开头；OR 回退又让 "most" 命中无关段落。修为 AND→OR 回退 + 命中词数排序 + 去虚词。
- 结果：读页能返回 MFN 相关段落，模型承认信贷协议存在，但仍答「信贷协议没有 MFN」——它没读到 Section 2.15(d)-(e)。缺口转为**按章节定位**（`doc_read` 增 `section`，或按标题树切块），超出时间维度计划。

### 13.4 `doc_read(section=…)` 与收口（2026-10-20 收尾）

`doc_read` 增 `section`：按 `Section 2.15` / `§ 2.15` / `2.15.` 找到标题块，从那里往后读 8 块；找不到回退普通读页并回 `section_found=false`。第五次冒烟：模型用了实体+类型+日期组合、拿到唯一卡片、读了该协议，但**没用 `section`**（不知道条款号），`head` 读 4000 字符正好停在 Section 2.15 之前，最终仍答「MFN 在 SAFE 里」。

收口：时间维度检索已足够（实体定位、日期排序、区间过滤、权威卡片），剩余是「条款先验」——不知道条款号时，关键词只能命中定义页。要做只能建条款索引（文档类型 → 条款号），不是检索时间维度的事。判官 gpt-5.5 当晚持续挂起，所有结论基于人工读答案。
