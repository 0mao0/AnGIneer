## 三、变更清单

### 变更 0：env 止血（R2，当天）

- **修改原因**：二排 52% duel 否决白烧（〔对方〕统计，机制〔实测〕），每次成功检索多花 1.5~5s。
- **修改目的**：省固定开销；拿 nightly 数据定二排去留。
- **修改方法**：服务器 `.env` 一行（手动维护，gitignored）：
  ```
  ANGINEER_LLM_SECOND_RERANK=0
  ```
  改完 `cd docker && docker compose up -d aichat-api` 重建（restart 无效，env_file 建容器时固化）。
  **超时不动**：保持 10s fail-fast。理由：降级链是本地短语重排/原序返回（毫秒级〔实测〕），拉长超时=把快速失败变干等（30s 方案已被用户否决）；10~15s 段卡死若经探针证实占比可观，再议 15s——挂为变更 C 的附带产出。
- **检查方法**：
  1. `docker exec angineer-aichat-api printenv | grep SECOND_RERANK` 在值——**对账是验收物，不是可选项**（上一轮重建 env 没带上白做一次）；
  2. 同题复测思考面板：rerank 计时应不再含 1.5~5s 二排；
  3. 超时计数不高于基线：24h 基线 4 次（口径＝aichat 客户端 Read timed out；nginx 侧 499 全调用方另计 20~34 次/天，两口径不混用）；
  4. 二排 A/B 关闸判据：与**最近 3 个 nightly（二排开）**比 hit@1 配对差，|Δ|≤1.5pp（噪声地板：526 题 ~12% 翻转、净差 ±5 题≈±1pp，1.5pp 为带宽）→ 保持关闭；超带 → 回滚该行，改走 F4 分数门控（top1-top2 分差 >0.001 才进 wide pass）。**不设 0.5pp 阈值**——低于噪声地板测不出。

### 变更 A：F2 探针测试 ＋ F3 memo 在途登记（R1，核心修复）

- **修改原因**：见 R1。双跑在拥堵时放大（10-02 两路 rerank 各打满 10s 即双跑所致），空闲时负载恒翻倍。
- **修改目的**：同一请求只跑一份检索；等待可见、可取消；主路复用预检成品。
- **修改方法**（`services/angineer-core/src/angineer_core/agent_tools.py` 单文件为主，约 80 行）：
  1. F2 先行（TDD 红灯）：
     - 键一致性断言：`_search_memo_key(预检 kwargs) == _search_memo_key(主路 kwargs)`，**现状预期=绿**（`agent_configs.py:316` rerank 默认 True 已核），锁「键位漂移→memo 永不命中且零报错」的静默失效面；
     - 形态复现测试：假端口把单次检索钉 ~6s，断言第二次检索不发生——**F3 落地前必须红**。
  2. F3 三态 memo：成品→弹出复用（现语义）；在途→`Event.wait(上限)`，预检写完成品后唤醒；无条目→自跑（闲聊/表题/未预检，行为不变）。
  3. 等待上限公式：**Σ(各 rerank 端点超时) ＋ 召回 p90**，且 < `tool_timeout_s`×0.8（QA 路径默认 120，`agent_loop.py:167` 已核未被压小；sop_runner 是独立常量另一条路，勿混）。当前 1 端点 10s ⇒ 约 15s。
  4. 退出路径全部回落自跑：等待超时／`cancel_event` 置位／预检异常或 error 返回；等待不计入 retry。
  5. 可观测：等待时长经 `_prefetch_ms` 同族私有键（`_` 前缀不进 LLM 投影）进 tool_end 事件，思考面板显示「等待预检 X.Xs」。
  6. 开关 `ANGINEER_MEMO_INFLIGHT=1`（默认开，=0 回现状）。
  7. MarkerAllocator：**预检与主路共享同一实例**（route_pre 创建、随请求传递）＋取号加锁＋**号段附带与回收**（memo 成品附带已分配号段；预检失败/等待超时自跑时回收孤儿号段，防主路号段漂移 K3、K4 起跳）。
- **检查方法**：
  1. 四个测试锁全绿：①正常共享（同实例）②预检失败回收 ③等待超时后主路自跑不跳号 ④键位漂移即红；
  2. `test_search_memo.py` 全套＋angineer-core 回归；
  3. 生产验收：同秒双行分段计时归零；cite 重号 0；思考面板出现「等待预检」段且耗时归属正确。

### 变更 B：`_ONLINE` 双 env 拆分（独立提交）

- **修改原因**：二排开关是进程级，关掉连评测一起失去二排；在线与评测从此需要独立配置。**不与变更 A 捆绑**——机制变更与行为变更分离，出事才分得清哪半在坏，MEMO_INFLIGHT=0 才是完整回滚。
- **修改目的**：评测路径保留二排、在线路径独立开关。
- **修改方法**：新增 `ANGINEER_LLM_SECOND_RERANK_ONLINE`（在线路径读它，缺省回退旧变量名，向后兼容）；单独提交，变更 A 验收后部署。
- **检查方法**：评测 run 的日志有「LLM 二排计时」、在线 chat 没有；`printenv`＋两路径日志双验生效。

### 变更 C：R5 探针 → 分腿归因后修对应腿

- **修改原因**：dense 段构成未定（embed 等待 vs qdrant 检索），两个现成数据源矛盾 4~8 倍（生产落盘 default dense p50 1.92/1.45/1.14/2.45/2.44s（09-28→10-03，n=2/35/15/3/5）〔实测〕vs 对方表 p50 226~310ms〔对方，出处待钉〕）；冷/热测量已示冷启动占大头（冷=1.48/3.31s vs 热=0.20/0.35s〔对方〕），但 knowledge_index 1.7G→3.6G 的结构膨胀〔实测〕仍在。
- **修改目的**：三成分各归各的腿——冷启动→变更 F 保温；结构膨胀→量化/拆集合/VACUUM；右尾排队→变更 E（4c47）。不许再拿单一药方押三者。
- **修改方法**（探针约 1 小时）：
  1. 生产分时段批量取 default 库请求，逐请求关联：embed 的 nginx `upstream_time` 与 qdrant 检索客户端侧分段，出 p50/p90（**不用 max**）；
  2. 检查 knowledge_index.sqlite 空闲页占比（VACUUM 候选）与 qdrant optimizer/segment 状态；
  3. 钉死两份 dense 历史数据的口径差（retrieval jsonl vs ttft jsonl 字段边界、生产 vs 开发机）。
- **检查方法**：探针报告三句话结论（冷/结构/右尾各占多少）；冷启动占比高 → 变更 F 加码；结构膨胀 → int8 量化（2.4G→0.6G）或 GDP/FB 拆独立集合或 sqlite VACUUM；右尾 → 变更 E。落地后验收：非评测窗 default 库 dense p90 <1s。

### 变更 D：意图悬差双头排查

- **修改原因**：08:44 意图客户端 6.03s vs 网关 upstream 1.535s，4.5s 悬差在 nginx 之前；但该次含冷进程首分类成分（08:42 重建后 2.5 分钟），0204 时段 classify p90 5.2~5.7s 又跟评测窗走——冷启动、连接层、排队三头都要排。
- **修改目的**：白天同题意图 ≤2s。
- **修改方法**：连接头——httpx 连接池/keepalive/TLS 复用排查（embed requests 栈同秒秒回，佐证栈差异）；排队头——查分类与答案模型是否同 GPU 同队；冷头——变更 F 保温覆盖。
- **检查方法**：连接头修后白天意图 p90 ≤2s；排队头证据并入变更 E 交接包。

### 变更 E：DGX 交接包（只立案，不在本仓库修）

- **修改原因**：4c47 上 embed/rerank 服务两次卡死（10-02 20:49 ≥10s 自愈 ≤63s；20:53:44 双双 500→401×7→20:56 自愈），客户端调参防不住复发。
- **修改目的**：维护方凭包内数据直接定位服务端根因。
- **修改方法**：文档放 `D:\AI\DGX\`（交接通道），内容：两次卡死窗口 nginx access 摘录（精确到秒）、rerank 24h 分布（p50 2.4／p90 5.3／p99 10.05／max 157s〔对方〕）、逐日 499 计数＋**口径注释**（nginx 全调用方 20~34 次/天 vs aichat 客户端 4 次/24h）、分类排队疑点（变更 D 排队头）、变更 C 的右尾归因结论。
- **检查方法**：维护方第一次回访不追问「证据呢」。

### 变更 F：空闲保温探针（新增，治冷启动税）

- **修改原因**：08:42 全栈重建后 2.5 分钟的请求吃到冷启动税（qdrant HNSW 冷加载、sqlite 冷页、冷进程首次握手）；冷热同序列差 5~10 倍〔对方〕。R1 治理后单跑请求仍会在冷态踩满第一脚。
- **修改目的**：让 qdrant HNSW、sqlite 页缓存、LLM/embed 连接保持在热态，压平冷启动尾。
- **修改方法**：aichat 进程内调度（复用 nightly_control 同族机制），每 5 分钟一条固定轻查询跑 dense+sparse+rerank（默认库，固定 query，结果丢弃）；开关 `ANGINEER_IDLE_KEEPWARM=1`；探针耗时落 ops 指标（顺带成为免费的冷/热基线观测）。
- **检查方法**：重启容器后第 3 分钟起，外部同题请求 dense 段与热态差 <2 倍；探针自身耗时有连续曲线可查。
